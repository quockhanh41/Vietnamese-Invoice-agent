## 0. Global constraints

At the top because three milestones running lost their rationales to
summarisation while keeping their procedures. Every one of these can be
satisfied by code that passes all tests while proving nothing.

1. **Canonical order is `(issue_date, invoice_series, invoice_number)`, never
   arrival order.** This is the whole claim M4 exists to prove. `domain.budget.consume`
   already sorts; the serial join must walk the same order for persistence too.
2. **The serial join is ONE transaction.** Persist + profiles + duplicates +
   reconcile commit together or not at all. The batch must never end with
   invoices recorded and budgets not drawn against them.
3. **`signals` must keep seeing an empty profile.** `apply_invoice` runs in the
   serial join, *after* fan-out. Move it earlier and `PRICE_OUTLIER` silently
   stops firing — M4-B measured the self-inclusion ceiling at 1.79 for n=5.
4. **The 10× shuffle must be genuinely independent.** The natural key is
   `UNIQUE`, so an unrolled second shuffle hits `ON CONFLICT DO NOTHING` and
   measures nothing while passing. Rollback is load-bearing, and only the
   mutation check proves it.
5. **`route_outcomes` produces lists nothing consumes until M5.** Deliberate,
   not an oversight.
6. **A milestone is not closed until `make check` is green on the PUSHED commit
   and CI agrees.** Four milestones have now failed this; M4-C failed it because
   seven commits were pushed as one batch and CI first saw the tip.

## 1. Why this exists, and one thing measured while planning it

M4-D builds the batch half: `Send` fan-out, the wrapper function node, the
serial join that persists and reconciles, and
**`test_budget_serialization.py`** — the third of the six tests §8 of the plan
calls the portfolio.

It also pays two debts M3-C recorded and M4 inherited: a per-run `thread_id`
(§8.5) and proof that the enrichment graph survives being wrapped as a function
node (§8.3).

### 1.1 The gate batch drifted, and its own guard could not see it

`scripts/generator/gate_batch.py` freezes 30 invoice ids with a per-id comment
generated by M4-A's discovery script. Two of them read:

```python
"INV-0122",  # IT / IT_SERVICES — clean
"INV-0123",  # ADMIN / OFFICE_SUPPLIES — clean
```

Measured 2026-08-01: in the current corpus both are **`unreadable_pdf`** —
deliberately corrupt files, not clean, not XML. M4-B's regeneration changed the
`new_vendor` allocation and the outlier amounts, which shifted
`_allocate_indices` consumption, so the frozen ids now name different invoices.

M4-B's own plan said to re-verify the gate batch and re-derive it if red. It was
not red. `tests/test_gate_batch.py` asserts 30 distinct ids, that they exist,
that the five required defect groups appear, MKT-only membership, and the breach
chain — **nothing asserts source type or "clean"**, so the drift was invisible.

This is the third form of one pattern. M4-A found a guard that was genuinely red
at the commit that introduced it and blind two commits later. M4-B found an
honest measurement recorded and then not acted on. Here a frozen list's
**documentation** went stale while its **assertions** kept passing. The common
root is that a guard proves only what it asserts, and what it asserts drifts away
from what it is believed to cover.

**Resolution: keep them, deliberately.** Two corrupt PDFs inside the gate batch
exercise a gate criterion — *one corrupt file does not kill the batch* — inside
the gate itself rather than in a contrived side test. They are relabelled
honestly, and §5 adds the two assertions that would have caught the drift.

### 1.2 The gate can replay hermetically — verified, not assumed

`classify_node` calls `run_classify(data, gateway=gateway, calls=calls)` with no
vendor argument, so its prompts are identical to those M4-C recorded. Checked
2026-08-01: **5/5 gate-batch invoices replayed classify and audit from the 762
committed fixtures with `GROQ_API_KEYS`, `GEMINI_API_KEYS` and
`OPENROUTER_API_KEYS` all unset.**

The two `unreadable_pdf` members need no fixture at all: M3-C's
`test_a_truncated_pdf_reaches_manual_queue_without_spending_a_token` established
that they reach `manual_queue` without a model call.

So M4-D's gate runs in CI with no key. That is the property M3 built `LLM_MODE=replay`
for, and this is the first milestone whose gate actually depends on it.

## 3. Components

### 3.1 The graph

```
START → ingest → cost_gate
cost_gate ─cond→ { rejected: END, ok: fan_out }
fan_out ─cond(list[Send])→ enrich_one
enrich_one → serial_join            ← implicit join: every Send completes first
serial_join → route_outcomes → finalize → END
```

`ingest` creates the `batches` row (`repositories.batches.create_batch`) and
resolves the input list. `finalize` calls `complete_batch`.

The join is implicit: LangGraph runs every `Send` before the next superstep, so
`serial_join` sees all of them. That is the property the whole design rests on,
and §4 tests it rather than trusting it.

### 3.2 `enrich_one` — a wrapper function node, not a compiled subgraph

Design §4.1 gives two reasons and M3-C §8.3 recorded that neither was ever
proven:

- **Explicit state mapping.** The wrapper builds `EnrichmentState` field by
  field rather than letting LangGraph match keys by name — design §4.1 calls
  implicit matching the number-one source of incomprehensible LangGraph bugs.
- **`try/except` per task.** A file that raises puts an entry in
  `state["failed"]` instead of killing the superstep. Without it one broken PDF
  ends a 30-invoice batch.

`thread_id` becomes **`enrich:{batch_id}:{invoice_id}`**. M3-C §8.5 recorded that
`enrich:{invoice_id}` is stable across re-runs, so a second batch would resume
the first batch's checkpoints rather than starting clean.

### 3.3 The serial join — one node, one transaction

Constraint 2. Inside a single `get_engine().begin()`:

```
ordered = sorted(survivors, key=(issue_date, invoice_series, invoice_number))

for inv in ordered:                       # canonical order, not arrival order
    ensure_vendor(...)
    invoice_id = insert_with_lines(...)   # None => the natural key already
                                          # existed => DUPLICATE_INVOICE
    vendor_profile.apply_invoice(...)     # AFTER signals ran (constraint 3)
    near_duplicate findings                # needs the corpus-wide view a
                                          # fan-out task cannot have

for dept in sorted(departments_present):
    SELECT ... FOR UPDATE on the budget row
    domain.budget.consume(limit, warn_pct, inputs)
    record_consumption(...) per invoice    # balance_before/after/sequence_no
    raise BUDGET_BREACH / BUDGET_WARNING
```

**`insert_with_lines` returning `None` is the exact-duplicate detector.** It is
`ON CONFLICT DO NOTHING … RETURNING`, so a repeated natural key yields `None` —
design §2.3's UNIQUE index doing the work, with no second implementation to
disagree with it.

**Departments are walked in sorted order** for the same reason invoices are:
two departments never contend for one budget row, but a deterministic lock order
is free here and removes a class of question that would otherwise need an answer.

## 4. `test_budget_serialization.py`

Portfolio test 3 of 6. Ten shuffles of arrival order at the **persist+reconcile
layer**, each inside a rolled-back transaction; assert the `balance_after` chain
is byte-identical across all ten and that the **same** invoice breaches.

**Why not the full graph ten times.** The agents cannot affect ordering — they
never touch it — so running them ten times tests the wrong layer. And each run
would have to persist the same 30 invoices, whose natural key is `UNIQUE`: runs
2 through 10 would hit `ON CONFLICT DO NOTHING`, insert nothing, and measure
nothing while passing. That is precisely the "passed exactly once per database"
defect M3-A's review found, and it is worth not rebuilding.

**Rollback is load-bearing** (constraint 4). A bug in the isolation scaffolding
makes the shuffles non-independent while the test stays green, so the test is
only trustworthy once **removing the canonical sort turns it red** — that
mutation is the evidence, not the passing run.

Separately, **one end-to-end batch run** through the compiled graph, replayed
from fixtures, proves the pipeline works and the implicit join holds.

## 6. Success criteria

1. **Exact agreement** between what the batch flags and what
   `corpus/gate_batch.json` declares. The auto/flagged split is *reported*, not
   targeted.
2. `test_budget_serialization.py` green across 10 shuffles, and
   **mutation-verified red** by removing the canonical sort.
3. The two `unreadable_pdf` members land in `failed`/`manual_queue` and the other
   28 complete — one corrupt file does not kill the batch.
4. Declared breach is `INV-0001`; chain `35,000,000 → 15,000,000 → −5,000,000`.
5. `thread_id` carries `batch_id`; two batches over the same invoice do not
   collide. Mutation-verified by reverting to `enrich:{invoice_id}`.
6. `enrich_one` maps state explicitly; a raising task lands in `failed` without
   ending the superstep. Mutation-verified by removing the `try/except`.
7. Gate-batch assertions from §5 green and mutation-verified.
8. `docs/diagrams/batch_graph.mmd` regenerated, drift guard green.
9. Full gate runs under `LLM_MODE=replay` **with no API keys**.
10. Three ADRs written.
11. `make check` green **on the pushed commit**, CI green on that commit.

## 7. Risks

| Risk | Mitigation |
|---|---|
| Shuffle isolation is subtly broken, so all 10 runs measure the same thing and pass | Criterion 2's mutation is the proof. A green run alone establishes nothing here |
| `max_concurrency` ships unexercised | Stated in §2.2. The gate replays, so concurrency is untested against real limits. M4-C measured **177 Gemini rate-limits in a SERIAL run** — a live fan-out will hit that harder, and M5's first live batch should expect it |
| One transaction for the join means a late failure discards the whole batch's persistence | Accepted (constraint 2). The expensive work is not lost: `llm_calls` rows are written inline during enrichment and survive independently |
| The implicit `Send` join is assumed rather than tested | The end-to-end run in §4 exists for this. If LangGraph ever runs `serial_join` before every Send completes, the invoice count is wrong and the chain differs |
| Gate-batch comments drift again | §5's third test parses the comments and checks them against the corpus, so drift fails loudly instead of silently |
